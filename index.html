Prefill ≠ Decode

大 GEMM 更容易喂饱计算单元

矩阵的 batch/sequence 维度较大，同一份权重参与许多 token 的运算，算术强度较高。

KV CACHE

2.68 GB 教学估算

开场问题的答案

Decode 每步只生成一个 token，常常要重新读取大部分权重。此时计算单元再多，也可能在等 HBM——算力翻倍不等于速度翻倍。

讲解提示

把 Prefill 和 Decode 当作两种不同工作负载：前者重计算、后者重搬运。提高 batch 能提升权重复用，却会同时增加 KV 容量、排队时间和尾延迟。

Paged Attention

把 KV Cache 切成块，减少连续大内存与碎片压力。

把计算型 Prefill 与带宽型 Decode 放到不同资源池。

Speculative Decode

小模型先猜多个 token，大模型并行验证，减少串行步数。

先解决权重与 KV 的读取速度

低 batch Decode 的算术强度低，HBM 容量和带宽通常比峰值 FLOPS 更能影响逐 token 延迟。

优先：足够 HBM、量化、KV 管理、减少跨卡边界
固定顺序
  1. 定义模型与输入输出形状
  2. 算容量是否装得下
  3. 判断计算/带宽/通信瓶颈
  4. 最后才比较具体硬件
讲解提示

现场任选两个场景，让观众按“形状 → 容量 → 瓶颈 → 硬件”的顺序作答。若一上来就说 GPU 型号，把讨论拉回 token、参数、KV 与通信量。
